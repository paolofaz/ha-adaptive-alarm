# Adaptive Alarm v1.0.7 — Lovelace card element registration

## Fixed

In some Home Assistant installations, a custom-card JavaScript module is
downloaded and executed but its custom-element registration is lost when
the frontend later installs the scoped custom-element registry polyfill.
Home Assistant subsequently reports **"Custom element doesn't exist:
adaptive-alarm-card"** even though the backend logs show the Lovelace
resource already exists. This problem is documented in
[home-assistant/frontend#53890](https://github.com/home-assistant/frontend/issues/53890).

Adaptive Alarm v1.0.7 now:

- Uses only the native Lovelace resource in HA-managed storage mode when
  that registration succeeds, avoiding double-loading the same JS URL via
  the early frontend extra-module path.
- Retains the extra-module fallback for resource-mode YAML and storage
  registration errors.
- Re-checks custom-element registration after the `home-assistant` root
  element is defined, and registers the card again if HA replaced the
  native registry during startup.
- Includes a regression test simulating the exact registry replacement,
  not just a JavaScript syntax check.

## Installation and verification

Update via HACS, restart Home Assistant, and **hard-refresh the browser**.
The existing single-card YAML remains:

```yaml
type: custom:adaptive-alarm-card
title: Antifurto
```

Do not create extra Lovelace resource entries. Check the card itself,
not merely the server's "resource registered" log. If it still does not
render, open `/adaptive_alarm/adaptive-alarm-card.js?v=1.0.7` in the same
Home Assistant browser to distinguish a missing asset from a frontend
registration/runtime failure, and report a redacted browser Console error.

No modifications to the alarm engine, Zigbee2MQTT siren, HomeKit bridge,
physical actions or user dashboard layout.
